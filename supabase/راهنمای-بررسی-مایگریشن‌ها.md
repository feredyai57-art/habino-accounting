# راهنمای فارسی بررسی و آزمون مایگریشن‌های Supabase

این راهنما کمک می‌کند بفهمید فایل‌های SQL پوشهٔ `supabase/migrations` در پروژهٔ Supabase اجرا و ثبت شده‌اند یا نه. **وجود فایل در مخزن به‌تنهایی به معنی اجراشدن آن در پایگاه‌داده نیست.**

## روش پیشنهادی: مقایسه با تاریخچهٔ Supabase

### ۱. پیش‌نیازها

- ابزار خط فرمان Supabase (Supabase CLI) باید نصب باشد.
- ترمینال را در ریشهٔ همین پروژه باز کنید؛ همان پوشه‌ای که `package.json` و پوشهٔ `supabase` در آن قرار دارند.
- شناسهٔ پروژه (Project Ref) را از نشانی یا تنظیمات پروژه در داشبورد Supabase بردارید. مطمئن شوید به پروژهٔ درست، مثلاً محیط آزمایشی یا اصلی، وصل می‌شوید.

### ۲. ورود و اتصال به پروژه

در PowerShell اجرا کنید:

```powershell
supabase login
supabase link --project-ref <PROJECT_REF>
```

به‌جای `<PROJECT_REF>` شناسهٔ واقعی پروژه را وارد کنید. دستور ورود ممکن است مرورگر باز کند. اطلاعات ورود یا توکن را در فایل‌های پروژه قرار ندهید.

### ۳. مشاهدهٔ مایگریشن‌های محلی و ثبت‌شده

```powershell
supabase migration list
```

خروجی، نسخه‌های فایل‌های محلی را با نسخه‌های ثبت‌شده در پروژهٔ راه‌دور مقایسه می‌کند:

- نسخه‌ای که در هر دو طرف دیده می‌شود، در تاریخچهٔ Supabase ثبت شده است.
- نسخه‌ای که فقط محلی است، نیاز به بررسی دارد و ممکن است هنوز اجرا نشده باشد.
- نسخه‌ای که فقط در Supabase است، ممکن است از محیط دیگری آمده باشد یا فایل متناظر آن در این نسخهٔ پروژه موجود نباشد.
- در صورت مشاهدهٔ اختلاف یا خطا، پیش از هر اقدامی پروژهٔ مقصد و فایل‌های مرتبط را بررسی کنید؛ تاریخچه را با دستکاری مستقیم جدول‌های داخلی Supabase اصلاح نکنید.

### ۴. پیش‌نمایش تغییراتِ در انتظار

```powershell
supabase db push --dry-run
```

این دستور فقط پیش‌نمایش می‌دهد و مایگریشن‌ها را اعمال نمی‌کند. خروجی را بررسی کنید تا مشخص شود کدام تغییرها قرار است روی پایگاه‌دادهٔ متصل‌شده اعمال شوند. اگر مقصد، تاریخچه یا محتوای تغییرها روشن نیست، ادامه ندهید.

پس از بازبینی و اطمینان از انتخاب پروژهٔ درست، اعمال تغییراتِ در انتظار با دستور زیر انجام می‌شود:

```powershell
supabase db push
```

این دستور **تغییر واقعی در پایگاه‌داده** ایجاد می‌کند. ابتدا در پروژهٔ آزمایشی اجرا و نتیجه را بررسی کنید؛ برای محیط اصلی، از پایگاه‌داده نسخهٔ پشتیبان داشته باشید و تغییرها را با دقت بازبینی کنید.

## بررسی نتیجهٔ یک مایگریشن مشخص در SQL Editor

برای نمونه، فایل `20261104_client_credit_metadata_fallback.sql` ستون `metadata` را به جدول `public.clients` اضافه می‌کند. در داشبورد Supabase، پروژهٔ درست را باز کنید و در **SQL Editor** این پرس‌وجو را اجرا کنید:

```sql
SELECT
    table_schema,
    table_name,
    column_name,
    data_type,
    is_nullable,
    column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'clients'
  AND column_name = 'metadata';
```

اگر یک ردیف با `column_name = metadata` برگردد، ستون مورد انتظار اکنون وجود دارد. این فقط نتیجهٔ آن تغییر را بررسی می‌کند؛ **ثابت نمی‌کند همهٔ مایگریشن‌ها اجرا شده‌اند یا این ستون حتماً با همان فایل ساخته شده است.** برای وضعیت کلی، از `supabase migration list` استفاده کنید.

## اگر SQL را دستی در SQL Editor اجرا کرده‌اید

اجرای دستی یک فایل SQL ممکن است تغییر را در شِمای پایگاه‌داده ایجاد کند، اما الزاماً نسخهٔ آن فایل را در تاریخچهٔ مایگریشن‌های Supabase ثبت نمی‌کند. در این حالت:

1. ابتدا با پرس‌وجوی مناسب، نتیجهٔ مورد انتظار را بررسی کنید.
2. تاریخچه را با `supabase migration list` هم مقایسه کنید.
3. اگر فایل در تاریخچه ثبت نشده، همان فایل را کورکورانه دوباره اجرا نکنید؛ ابتدا مشخص کنید آیا همهٔ دستورهای آن قبلاً اجرا شده‌اند و روش امن هماهنگ‌کردن تاریخچه را بر اساس وضعیت پروژه انتخاب کنید.

برخی مایگریشن‌ها چندین جدول، سیاست دسترسی یا تابع پایگاه‌داده را تغییر می‌دهند؛ بررسی یک ستون برای تأیید آن‌ها کافی نیست. نتیجهٔ مورد انتظار هر فایل را جداگانه و با پرس‌وجوهای متناسب با همان تغییر بررسی کنید.

## تفاوت آزمون‌های برنامه با آزمون پایگاه‌دادهٔ راه‌دور

دستورهایی مانند `npm run test:security` یا `npm run test:core-accounting` آزمون‌های برنامه در محیط محلی هستند. موفقیت آن‌ها به‌تنهایی نشان نمی‌دهد SQLهای Supabase روی پروژهٔ راه‌دور اجرا شده‌اند. برای بررسی اجرای مایگریشن‌ها، از مقایسهٔ CLI و بررسی نتیجه در پایگاه‌داده استفاده کنید.
